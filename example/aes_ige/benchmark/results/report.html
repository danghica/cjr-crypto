Project index

Results are normalized by the shared project benchmark runner. Median and IQR are shown for each configured workload and implementation.

Throughput units
ns/op is ns per logical message byte for encrypt/decrypt. Each sample includes IV reset and full output checksum.
Key setup units
ns/op is ns per forward schedule expansion, including round-count validation and expanded-schedule checksum. OpenSSL inverse schedule setup is excluded from decrypt throughput and is not measured.
Validation
All output bytes and final IVs independently compared before timing; differential.json records the result. Timed batch checksums are also checked.
Comparison limits
Packed-byte OpenSSL C versus Int64-byte Cangjie; a practical implementation comparison, not an isolated language comparison. See openssl-metadata.json for C compiler, library digest, version and dispatch caveats.
Possible causes of the speed difference (not definitive)
The timings establish a performance gap for these workloads, but do not identify its causes or quantify their individual contributions. The explanations below are hypotheses based on implementation differences. Profiling and controlled comparisons would be needed to establish causality; the gap cannot be attributed to C versus Cangjie alone.
Observed OpenSSL code path
Inspection of the installed OpenSSL 3.6.1 library shows AES_ige_encrypt calling the software, table-based AES_encrypt/AES_decrypt routines. This inspected path does not call the ARM hardware AES routines, so hardware AES instructions are not an explanation for this particular comparison. This observation is specific to the recorded library build, not every OpenSSL implementation.
Possible cause: combined round operations
OpenSSL’s software AES uses precomputed tables and packed 32-bit words to combine substitution, row shifting and column mixing into table loads and XORs. CJR performs these transformations separately. Fewer operations and intermediate state transfers may contribute to the gap, but their contribution was not measured separately.
Possible cause: branch-heavy substitution
The extracted S-box uses a nested decision tree, evaluated for sixteen bytes in each AES round. Branch execution and possible mispredictions may cost more than indexed lookup. The benchmark does not establish how the compiler lowers these branches or how many mispredictions occur.
Possible cause: representation and memory traffic
CJR represents each AES byte as an Int64 word and passes state through workspace buffers between transformations. OpenSSL uses packed words and register-held state. Larger buffers and repeated loads/stores may contribute to the gap; eightfold byte storage does not imply an eightfold timing penalty, and the benchmark does not isolate memory or cache costs.
Possible cause: extra decryption work
CJR implements inverse MixColumns by applying forward MixColumns three times. This simplifies the algebraic proof but performs extra transformations, which may help explain the larger decryption gap. The timings do not isolate this cost or prove that it accounts for the observed ratio.
Proofs and possible optimization directions
Formal proofs are checked separately and add no runtime work to the extracted AES routines. Any runtime cost comes from the executable design and generated code. Candidate optimizations include direct S-box lookup, fewer intermediate buffer writes, packed state and direct inverse MixColumns, each with corresponding correctness proofs. Their performance benefits remain to be measured.
